# 步骤 2 — 选择容器与组装系统

由编排者亲自完成：本步骤询问用户，然后写 `docs/system-profile.md`。

**输入：** `docs/deconstruction.md`。**输出：** `docs/system-profile.md` —— 后续每一步都会读取的组装记录。
它不承载情节。

## 1. 选择主容器

除非用户已指定形态，否则引导用户在下列四种容器中选择，并基于小说特征给出建议；
建议列在最前并标注"（推荐）"。如果有提问工具可用，询问一次并等待决定；
否则按建议继续，并在 profile 中标注"容器为推荐值，待用户确认"。

| 容器 | 玩家幻想 | 核心交互 | 路由条件（小说特征） |
|---|---|---|---|
| **A 假官方网站** | "我正在入侵某个组织的网站。" | 站点自身的信息架构 + 下面选定的模块 | 单一组织即舞台（餐厅 / 公司 / 学校 / 教会）；秘密藏在本应保持私密的页面里；失踪或掩盖事件的调查 |
| **B 假电脑桌面** | "我拿到了别人的电脑。" | 桌面图标 + 应用页（聊天 / 邮件 / 云盘 / 日历） | 某个视角角色有合理途径接触他人设备；线索散落在多个"应用"中；推进依赖密集的密码门 |
| **C 模拟互联网** | "我在对一个消失的人做互联网考古。" | 多个相互独立又互相链接的"网站"（论坛 / 博客 / 网页时光机 / 内网），需手输网址 | 时间跨度长（多年日记 / 年度博客）；线索散布在多平台；虚构可以打破第四面墙 |
| **D 档案系统** | "我在调阅一份封存的卷宗。" | 查询表单（姓名 / 编号 / 日期）→ 档案列表 → 详情页，每页只对它所指向的账号开放 | 小说以文件驱动为主（卷宗 / 病历 / 审讯笔录 / 户籍）；冷淡的公文腔；调查者是警察 / 记者 / 律师 |

**路由顺序。** 主要信息载体：聊天记录与文件 → B；文件与档案 → D；网页 → A；跨平台碎片 → C。
玩家的叙事角色必须能合理接触该容器——若不能，增加一个入口页说明它是如何获得的
（借来 / 继承 / 黑入 / 正式调取）。允许混用：主容器内可嵌套一个次级容器；嵌套深度为一级。

## 2. 选择设计模块

容器决定原生触达模型（A：搜索 + 密码门；B/C/D：账号登录 + 按账号授权）；
其余一切机制都是 `references/design-playbook_zh.md` §2 里的模块——换肤、禁词状态、
进度编号、收集载体、结局、分阶段演出、遥测。与用户一起选择，推荐项列前；虚构用不到的模块
不得启用，没有身份设定的故事不得附送账号家具。显式询问换肤（M5）：玩家跨入秘层时，
故事是否需要可见的变化，还是这个系统从不露出接缝？两种答案都成立——记录下来；
只有当虚构支持时，才提供戏剧化的访问级别换肤。感官需求（M12）仅在站点确实实现时才声明
（耳机、鼠标、光线）。

## 3. 写 `docs/system-profile.md`

```text
# System Profile
- 容器：A/B/C/D（+ 嵌套的次级容器）及理由
- 虚构：系统类型、组织、年代、语言、语域
- 触达模型：选定的模块（M1…M13），以及每层深度靠什么跨越（搜索 / 密码门 / 账号 / 手输网址）
- 呈现：换肤、禁词状态、进度编号、收集载体——各自是/否
- 包裹层：入口页、结局、第四面墙收尾、世界纹理——各自是/否
- 交互：分阶段演出、假交互、感官、遥测——各自是/否
- 外壳信息架构：顶栏项、目录布局、页面根目录、站点根目录（C）；这类系统都有的基础页
- 索引 / 访问约定：按受众分表（A）或单一索引 + 账号矩阵（B/C/D）
- 基础设施：base.md 章节、components.js、内置 Alpine、tools/、检查器 CONFIG 旋钮
- 待用户确认的问题
```

无论选择哪个容器，其形态文档都是步骤 3 与 6 的必读：
`references/structure/form-website_zh.md`（A）或 `references/structure/form-system_zh.md`（B/C/D）。

本步骤的基线测试陷阱：`references/common-mistakes_zh.md` §2 —— 交回产物前逐条检查。
